A studio of two instincts.

Qintara is a small interface practice. One foot in design research, one in production front-end — deliberately in the same room, because most interface failures happen in the handover between them.

Practice note / 2026

01 — Position

Interfaces are instruments before they are screens.

A tool is legible when its state is visible while you act. That is true of a plane, a camera and a well-made form. Most software hides its state behind confirmation dialogs and success toasts, then asks people to trust a message instead of the evidence in front of them.

We work on the part of a product where that evidence matters: the measurement panel, the archive, the live console, the studio's own portfolio. Our method is unglamorous — watch the work, find the sentence the interface is failing to say, prototype it in the medium, then remove whatever is left over.

We are not a growth agency and we do not run campaigns. We take a small number of engagements where the interaction itself carries the value.

02 — Principles

Five rules we keep arguing about.

These are working principles, not values on a wall. Each one has cost us something on a project.

01

State beats decoration

Every screen should be able to answer "what is happening right now?" before it answers "how does this look?". Decoration earns its place only when it shortens that answer.

02

Type is the interface

Most interfaces are made of words. A scale, a measure and a consistent rhythm do more for clarity than another component library. We choose typefaces for their behaviour at small sizes and in two languages.

03

Motion explains, never performs

Animation is allowed when it shows a change of state or a relationship between two things. It is not allowed to delay a task, and it always has a reduced-motion path that is designed rather than disabled.

04

Small dependencies, long life

A static site with no runtime framework can still be opened in five years. We prefer the platform: semantic HTML, modern CSS, a small module of JavaScript where behaviour is genuinely needed.

05

Say what is not known

A portfolio is a claim about capability. Where we cannot show evidence, we say so — which is why the case studies on this site describe signals we would watch rather than results we did not measure.

03 — Method

Four movements, repeated until the thing is right.

01

Observe

Watch the work happen. Record the verbs people use, the numbers they re-check, the moments they stop trusting the screen.

02

Name the problem

Write it as one sentence the client would recognise. If it needs three sentences, the project is not scoped yet.

03

Prototype in the medium

Build the risky part in the browser at week two. Static comps are for composition; feel is only decided in code.

04

Leave a system

Tokens, documented components, and a written rationale travel with the build, so the next team can extend it without archaeology.

04 — About this build

An honest note about what you are reading.

This site is a demonstration portfolio. "Qintara" is an invented studio identity created for the exercise; the four case studies are written examples, not delivered client work. They were written to show the structure of a real case study — context, constraint, decision, trade-off — without inventing testimonials, awards or metrics.

The contact address is a reserved placeholder ({{domain}}) and the enquiry form composes an email in your own client rather than sending anything to a server.

05 — Limits

What we are not.

We are not a full-service agency: no campaign planning, no media buying, no large-scale 3D production. We do not run generative AI features inside client products as a default. If a project needs a team of twelve, we will say so in the first meeting.

The instrument on the home page is a working component, not a video. If it does not respond, the site explains what it should have done — we would rather ship a fallback than a decorative lie.
