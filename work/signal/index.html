Case 03 — Data interface

Signal

An on-call console for a platform team. The old dashboard was not missing data — it was hiding the shape of it behind averages.

Demonstration case study — fictional client

Client
Fictional brief, written for this build
Sector
Developer tooling, observability
Scope
Information design, chart system, front-end
Team
One designer, two engineers
Modelled window
14 weeks
01

Context

Engineers were responding to roughly forty alerts a week, most of them noise. The dashboard drew every metric in the same weight and the same palette, so the eye had no way in. Worse, it plotted averages: a service where 4 % of requests took two seconds looked identical to one where everything was slow.

The team's own description was the brief. "By the time we open the dashboard, we already know it is broken. We need to know what shape the breakage has."

Context

Used at 3 a.m., on a laptop, by someone who has not slept.

02

Constraint

The real limits

  • Density. Nineteen metrics had to remain visible at once; nothing could be hidden behind a tab.
  • Design system. Tokens and component APIs were fixed; only the page composition could change.
  • Live data. Panels updated every fifteen seconds and could not shift the layout.
  • Colour. A meaningful share of the team reported some colour vision deficiency.
03

Decisions

Show the band, keep the median.

Every chart shows a distribution band with a solid median line, so a bimodal latency chart reads as two populations rather than a comfortable average. Trade-off: more ink per chart; the page had to lose two secondary panels to pay for it.

One accent, earned by state.

Series are drawn in ink and grey; the single vermilion is reserved for "outside expected range". Trade-off: series are distinguished by position and label rather than hue, which is slower on first glance but survives colour-vision deficiency.

The URL is the state.

Time range, service and focus are encoded in the address, so an engineer can paste a view into an incident channel. Trade-off: no transient UI state; anything worth keeping had to be made addressable, which required negotiation with the team.

04

Craft

Rendering rules

  • Charts render to canvas for volume, but every chart has a data table alternative in the DOM.
  • Panel height is reserved before data arrives, so a 15-second refresh never moves the page.
  • Numbers use tabular figures and fixed decimal places; a value changing width is a distraction at 3 a.m.
  • No animation on data refresh — only on state change, and never longer than 200 ms.

Reading order

The page opens on one sentence generated from the data: which service, which signal, how far outside its band. Everything below is evidence for that sentence. This was the largest structural change and the one the team resisted most, because the old page opened with a wall of charts that felt authoritative.

Accessibility

Every chart exposes a summary and a table; colour is never the only encoding.

05 — Signals

What we would measure.

This brief is written, not delivered, so no outcomes are claimed. These signals reflect what actually matters to an on-call team.

  • S1

    Alert-to-cause time

    From page to the sentence that names the likely cause.

  • S2

    Slow-burn detections

    Incidents caught by a person before a user reported them.

  • S3

    Views pasted into incidents

    Whether addressable state is actually used in the middle of an incident.

  • S4

    Alerts muted per week

    A falling number means the console earned its colour.
